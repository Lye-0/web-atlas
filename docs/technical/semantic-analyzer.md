# Analyzer View 6–10

## Data path

`scanProjectFiles` collects supported sources alongside the existing configuration and module facts. `AnalyzerProjectStore.semanticSources` contains a syntax-preserving mask of sensitive literal values; `sources` retains the existing masking contract for Views 1–5. File and line offsets are preserved. Neither source collection is persisted across browser reloads or uploaded.

Opening a semantic View starts `semantic/semantic.worker.ts` through `semantic/client.ts`. Analysis is cached by project-store identity, shared between the five Views, and reports file progress. The user can cancel or retry. Selecting or rescanning a project creates a new store and resets View state and imported execution data. Parser trees are deleted after each file, and the Worker terminates when analysis finishes. Parser runtimes and grammars are bundled as same-origin WASM assets; only grammars required by the selected sources are loaded.

`semantic/analyze.ts` produces a separate `SemanticAnalysis`, preserving the existing `AnalyzerFact` model and projectors. The new page calls `projectSemanticView`; sending a semantic View to the older synchronous `projectAnalyzerView` is an error rather than a fallback to an unrelated View.

## Language and framework coverage

The browser uses Tree-sitter grammars for TypeScript, TSX/JSX, JavaScript, Python, Java, C#, Go, Rust, Ruby, PHP, C, C++, Swift, Kotlin, Scala and Dart. Kotlin and Scala use an isolated legacy parser ABI; all other grammars use the current parser runtime. Vue and Svelte retain original offsets while parsing their script blocks; template analysis is reported as partial. SQL, Prisma and GraphQL use focused schema parsers, with comments excluded before extracting definitions.

Framework handling is syntax-based, not dependent on running or installing the target project:

| Surface | Recognized forms |
| --- | --- |
| UI and events | React JSX event attributes, DOM `addEventListener`, extension `registerCommand` / `onDidReceiveMessage`, named runtime callbacks and event registrations |
| JavaScript/TypeScript servers | Express/Hono-style HTTP method registrations, Next App Router and Pages API exports, SvelteKit server exports, Nest-style Controller and method decorators, Worker `fetch` / `scheduled` / `queue` |
| Python | FastAPI/Flask decorators, Django `path` / `re_path` and imported handlers |
| JVM / .NET | Spring mapping annotations, ASP.NET route attributes and minimal API method registrations; controller prefixes are composed with method paths |
| Go / Rust / Ruby / PHP | net/http and Gin-style registrations, route/get/to forms, Ruby route DSL and controller references, Laravel-style `Route` registrations |
| Data definitions | Interfaces, type aliases, classes, structs, records and fields; Zod objects, Drizzle tables/views, Mongoose schemas/models, Sequelize definitions, model inheritance, Prisma/SQL/GraphQL schemas |
| Operations | HTTP requests, recognizable database/storage/auth calls, native process/filesystem calls and message operations |

This is a cross-language structural analysis, not a complete compiler or framework runtime. Language grammar errors and unsupported template regions appear in per-file coverage. Framework factories, computed configuration, unrecognized route mounting, indirect dispatch, overloaded methods, reflection, macro expansion, complex import resolution and heap aliases can remain unresolved. Paths inferred from file routing, route patterns, service bindings or naming retain their confidence and evidence.

## Semantic contracts

Nodes identify functions, entries, requests, operations, values, models, resources, subsystems, external targets, spans and logs. IDs include source path, source range and symbol identity; they remain stable for an unchanged scan. Different calls in a fluent expression are identified by their complete AST ranges, including calls with the same start offset. Relationships retain source/target IDs and exact evidence ranges. Selection does not alter these relationships.

Confidence is explicit:

- `source`: a declaration or relation directly supported by source syntax.
- `inferred`: a possible correspondence, callback contract, branch-dependent value, or responsibility classification.
- `observed`: a record or explicit relationship in imported execution data.
- `unresolved`: a call target that cannot be uniquely resolved within available source and bindings.

Local call resolution prioritizes the nearest lexical declaration, explicit `this`/`self` class context and import bindings. An unknown `obj.method()` receiver stays unresolved even when a local function has the same name. Languages with implicit instance calls may resolve the current class; JavaScript/TypeScript bare calls do not implicitly become `this` calls. The TypeScript grammar's `await_expression` function operand in a generic call is unwrapped before name resolution; the complete call and argument evidence range is retained. Explicit re-exports can be traversed; ordinary imports do not re-export their dependencies. Parameter/local shadowing is preserved. Known callback-taking APIs support both inline and uniquely resolved named callbacks, with inferred `callback` edges rather than direct call edges. Passing a function to an unrecognized API does not establish callback execution.

Data values represent parameters, assignments and returns. Views 8–9 add a closed in-memory TypeScript refinement for source occurrences, property paths, call-site arguments/results, model kinds, field provenance and explicit expansion states. Conditional assignments retain possible preceding definitions; contextual call paths do not exchange independent calls' inputs. Large/deeper callee paths use explicit source-referenced summaries. Name-only database destinations are removed from the Data Flow projection while independent Runtime memberships remain unchanged. This is conservative source-level analysis, not SSA, a taint proof or runtime reachability proof. The exact supported formats, relation directions, expansion limits and shared explorer contracts are specified in [Data Flow / Data Model](tabs-8-9-data-analysis.md).

## View projections

| View | Main entities and relationships |
| --- | --- |
| Runtime Flow | Entry points, UI events, requests, operations and resources. Registration owner → event entry and entry → handler are distinct source relationships. Only unambiguous serial helper chains are compressed. Branch/merge boundaries on relevant runtime paths remain nodes, preserving all sides of convergence without enumerating every complete path. Compressed edges retain original relation IDs, kinds, confidence and evidence. Configured runtime entry files link runtimes with handlers. Unique HTTP route matches are inferred. |
| Function Call Flow | Function declarations and actual call sites, unresolved/external targets, and inferred callbacks for known callback-taking APIs. |
| Data Flow | Parameters, values, intermediate operations, arguments, return results, serialization/validation and persistence. |

## Execution data

The file input accepts JSON or JSON Lines, with a 20 MiB file and 20,000 record limit. Supported shapes include OTLP `resourceSpans` / `resourceLogs`, Jaeger traces with processes/references/logs, Chrome complete events and explicit begin/end scopes, and generic structured spans/logs. Unsupported Chrome phases and missing parent spans are reported. A structured log carrying a span ID remains a log.

Parent/child relationships use recorded IDs. Chrome begin/end scopes use their explicit per-process/thread nesting; complete events are not assigned parents merely because their timestamps overlap. Records without correlation remain separate. OTLP nanosecond and Jaeger/Chrome microsecond durations are converted to milliseconds.

Supplied start/end/event clocks are retained as strings, together with the input format, source filename and known clock unit/origin. OTLP nanosecond strings are never converted to `Number`; millisecond duration is a separate derived value. Jaeger start/log timestamps, Chrome `ts` and explicit end-event `endTs`, and generic supplied timestamp fields remain available in detail. Missing end times or correlations are not synthesized from duration or nearby events.

Source and execution layers can be displayed separately or together. A unique `code.file.path` / function / line correspondence links a span to the source; name-only matching is marked inferred. Sensitive attribute keys are masked. Observed Data Flow requires explicit `data.input.name` and/or `data.output.name` attributes; these create input → span → output relationships. Arbitrary log prose is not converted into data lineage.

## Exploration and rendering

`SemanticAnalyzerPage` routes Views 6–7 to `FlowAnalyzerPage`; Views 8–10 retain the earlier object-list/page renderer. Source analysis and imported execution data remain shared by store identity. Test code and generated definitions are hidden initially and can be included explicitly. Responsibility, kind, confidence, source/observed/combined layer and explicit cross-View membership filter the target collection. Query, selection and the 2D relation center do not filter the global collection. Relation depth belongs to the local 2D visit; relation direction is shared between modes and filters lines relative to the selected object while retaining the node collection and coordinates.

Views 5–7 share the project/view heading, search control and fixed-height `SearchResultStrip`. Search is literal, case-insensitive AND across whitespace-separated terms with trim and Windows/POSIX slash normalization. Search documents explicitly allow names, definition paths, ownership/group names and registered aliases; meaningful model fields remain supported. Internal IDs, arbitrary metadata, confidence flags and layout values are excluded. Ranking is exact name, name prefix, name substring, then path/group/field matches. Results expose match reasons and complete identifying paths in title/detail. The horizontal virtual row represents every match; its width and `aria-setsize` reflect the full result set. Card width is capped at 256px and shrinks to the measured row width minus two 4px focus gutters. Virtual stride, track width and focus reveal all use that same geometry. Home/End and arrow navigation can mount/focus any result, and focus scrolls only the strip. Resize keeps the focused candidate mounted and fully reveals it after the new track width commits. Scrolling retains a keyboard entry among visible results. Composition events cannot implicitly select a candidate.

Query produces result IDs and highlights while retaining the same graph object, node positions, location, camera and explicit selection. Search always covers the filtered View, including objects outside the current 2D folder. Choosing a result creates a meaningful visit: 2D opens its actual ownership and centered relations, and 3D focuses its canonical ID. Clearing query leaves selection and location intact. Counts distinguish canonical projection size, filtered objects, current scope children, local relations, and search matches. External result paths are identified as call sites. A filter-hidden selection keeps its detail with an explanation and restore action; a selection absent from the current source/execution projection is invalidated. New project stores reset selection, execution data and cameras.

The explicit filter-reset action replaces semantic options with their initial values, including clearing cross-View `members` context and disabling auxiliary/test/generated definitions. It does not merge a partial default into the previous filter object or write query, selection or camera state. A selected auxiliary object that becomes hidden retains its detail and the existing filter-hidden explanation.

Runtime model details retain fields, key/optional/type annotations and unresolved field spreads. Each selected object offers the other semantic Views as context links. `semanticNavigationContext` resolves a target through canonical ID, owner or explicit members; multiple owned values open the entire owner-scoped collection. An unrelated unique name is not enough to select a target, so unproven correspondence opens a definition-path search with no selected detail. Data Model navigation always uses the source layer; other targets inherit the current layer. Explicit context navigation frames the destination context and preserves its display-mode preference. Views 8–10 keep their existing return links, which can resolve the same canonical identity or owner when returning to Runtime/Function Call.

Views 6–7 use the Module Dependency detail proportions and disclosures. Relations are separated into outgoing, incoming and self, then grouped by canonical counterpart ID. Long counterpart and parallel-relation lists initially show six items and can be expanded completely. Each relation retains its own selection, kind, confidence and provenance. Node basic information, evidence, metadata and related Views start collapsed; model fields remain visible. Edge endpoints, relation information and evidence start open. Disclosures defer their content without removing any evidence ranges or cross-View destinations.

For Views 6–7, `semanticExplorer.ts` builds ownership once from the full View graph and the actual indexed file paths. View 7 opens project → directory → file → function/method/callback. Only the current scope's direct children are shown as ordinary readable blocks, filtered by the global visible IDs. The current file therefore does not render every function in the project. Click/Enter opens a block. The canonical node, its selection and its current ownership scope remain separate states. External nodes retain call-site evidence but never use that path as a function definition or offer a fabricated definition destination.

View 6 uses the same explorer controls. Runtime classification requires a recorded runtime resource and its exact configured entry file or explicit `runtime-entry` edge, or an observed `service.name`. Responsibility names and call reachability do not infer runtime membership. Zero or multiple runtime candidates enter the explicitly labeled unclassified context and its directory/file ownership. These rules also supply 3D region identities. Scope records and region bounds are presentation metadata; they are not canonical entities or relationships.

Opening a function creates a local caller → center → callee diagram with direct relations at depth one. Its center, hop depth and camera remain fixed when a neighbour is selected; explicit center and definition actions create new visits. Adjacent nodes in other files remain in the graph. The shared direction control filters displayed lines relative to the selected object, like the direction palette; it does not redefine the 2D center or collection. Unrelated background lines, internal relations and an explicitly selected edge remain visible. Without a selected node its value is retained but no directional line filter is applied. Adjacency indices bound traversal in both directions to the requested depth; the resulting local graph retains each traversed canonical edge, parallel call site, callback, cycle, self relation and provenance.

Choosing a relation from a neighbour's detail can select an edge outside the current local graph. The center remains unchanged, and the detail retains that canonical Edge ID and its evidence. The navigation identifies the outside relation and offers an explicit display action. That action, or the stage's selection-move action, opens the relation source's ownership and direct local relations while retaining the selected Edge ID. Back restores the previous center, camera and relation selection. Filter-hidden selections use the separate filter explanation and restore action.

The 2D block browser scrolls within the current scope; Fit, Reset and zoom controls are disabled there. A definition action opens the actual containing file and scrolls its selected object into view. Local diagrams without a saved camera use the plot area below navigation and above the legend. A diagram of at most twelve objects initially fits its cards and curves when that requires a scale of at least 0.8, capped at 1.05; otherwise it opens around the center at a readable scale between 0.85 and 1.1. Saved visit cameras take precedence. The 2D Fit and Reset buttons both frame the current local cards and displayed curves, including a larger graph that needs a smaller scale. The generic summary utilities remain available to other semantic renderers but no longer create an expanding project-wide 2D map for Views 6–7.

The local 2D renderer measures its SVG synchronously in a layout effect before its first paint; ResizeObserver handles subsequent size changes. Until usable dimensions and an initialized camera exist, it reports that relations are being displayed rather than painting a graph against a zero-size viewport. Only initialized cameras are persisted, focus commands wait for readiness, and disposed visits ignore late resize notifications. This does not add delayed rendering or change the existing initial/saved-camera rules.

`semanticFlowDisplay.ts` supplies human display names to 2D blocks, cards, navigation and search results without changing canonical records or search matching. A function with `attributes.initializer === true` is shown as file-level processing; a name equal to `<module>` alone does not trigger this conversion. Recorded external/operation callees are shortened by eliding nested arguments and bodies. Source paths/lines accompany titles; collisions add recorded source ranges, with distinct IDs retained in tooltips. The original label and callee remain available in tooltips and canonical detail/Evidence. An external target's displayed source path is a call-site example, not a definition location.

Whole-map 3D is independent of the current 2D scope. `flowCloud.ts` creates compact rotated volumes within files, then packs file and ownership groups in three dimensions. `flowUnresolvedPresentation.ts` separates unresolved external targets from those definition/ownership clouds. In the overview these targets have one synthetic display aggregate with no definition path or fabricated Evidence. Selecting a node reveals its directly connected unresolved targets; selecting an edge reveals both canonical endpoints. Explicit expansion shows every original target, and collapse retains those needed by the current selection. The complete filtered graph remains the input to search and canonical edge paths; detail continues using the full View's canonical relations and node index, including filter-hidden selections. No edge endpoint is remapped and no same-name targets are merged. Target counts count original graph objects, relation counts count incident filtered graph edges, and call-site counts deduplicate path/start/end of the retained `calls` edges' Evidence. Counts are explicitly scoped to the current filters.

Normal ownership points and unresolved member positions are fixed for a given filtered graph; neither selection, query nor expansion rearranges them or automatically moves the camera. A stable landscape aspect and inter-group gaps improve the initial overview; each group retains depth and can be orbited. Thin neutral wire outlines use the existing region extents and membership at the current display granularity. They have no filled faces, direction arrows, particles or hit targets. A region label frames its displayed canonical members without selecting a synthetic object. External-only group labels identify their display aggregation. The synthetic aggregate has a hollow ring marker, distinct from canonical filled points. Aggregate controls offer explicit expansion, collapse and paginated access to original IDs and details. The existing analyzer may identify several call sites with the same external file/callee object; separate call edges and source ranges remain the authority for those sites.

The 3D-only `分類の囲い` control initially shows these outlines at opacity 0.17. OFF changes only their visibility. The fixed-width control and the session-level `showFlowGroupBounds` preference preserve the plot size, coordinates, camera, selection, query and aggregation state. The preference survives Views 6–7, ordinary history and project replacement within the current app session. It does not add a browser-persisted setting.

3D labels reserve selected nodes and both selected-edge endpoints before direct neighbours and hover, followed by major regions and nearby representatives. A few visible neighbours can use additional offset positions ahead of unrelated labels; hover cannot displace an explicitly selected edge's endpoint labels. Names avoid their own dots, other labels and the measured disclosure bounds. Points covered by a disclosure are included in the remaining-connections notice. Lower-priority names are culled when they collide with points. Previous label sides and visible names receive hysteresis so small camera/zoom changes do not continually exchange labels. Offset node names have leaders to their exact dots; the computed reservation width is applied to the button so leaders also meet short labels placed left of a point. A pointer corridor retains the hovered name between its dot and label. A disclosure distinguishes offscreen connections from unlabelled onscreen connections and offers explicit movement to each original target, while detail retains the full relationship list. Movement from a disclosure closes it so the panel does not obscure the destination.

Lines and particles focus on the selected canonical neighborhood. Both modes use the Module Dependency palette: outgoing blue `#82c6e2`, incoming amber `#dfb785`, internal `#afcbbd`, always relative to source/target rather than screen position. The legend places the selected object between incoming and outgoing meanings, with View-specific wording. Unresolved-call details distinguish a recorded call expression from an unidentified function definition, label call-site paths explicitly, and retain every original relation and source range. Static arrows and relation endpoints remain when particles are off. Normal/reduced/off control, reduced-motion defaults, page/viewport visibility, and disposal on mode change/unmount limit animation. Particles explain a relation direction; they are not proof of an observed execution order.

Node role labels use those same displayed canonical source/target relations. Outgoing labels use a blue mark, incoming labels an amber mark, and reciprocal counterparts retain both marks and both roles. Pure Function Call `calls` use 呼び出し元／呼び出し先; pure `callback` relations use コールバック元／先; mixed kinds and Runtime use 入る関係／出る関係. Selecting an edge instead gives its endpoints explicit neutral 始点（Source）／終点（Target） labels, including a combined self-relation role. Classification labels remain neutral. Role and duplicate-identity rows contribute to the 3D collision reservation size.

Acquiring hover keeps an existing 3D label's compact dimensions. Full name and source information remain in its native tooltip and detail; selected labels retain their source row. Growing a left-side label on hover could invalidate its point clearance and move it away from the pointer, so hover does not introduce an extra row or wider hit box.

Hovering or focusing a point, label or detail counterpart emphasizes its existing relation set with the current selection. An individual edge or detail relation uses the exact relation ID, including recorded provenance. Other visible relationships remain present at reduced intensity; source/target, colors and particle settings remain unchanged. The page shares transient pointer/focus state with input ownership: the most recent unpressed pointer movement or focus wins, releasing it restores the other active input, and a late leave from another element cannot erase the current target. Pointer entry caused by layout or focus scrolling does not acquire hover; dragging also does not change the counterpart. Selection, filtered graph, direction, mode, View, scan or explorer visit changes invalidate old inputs. Detail row removal and 3D label culling release only their acquired input. Query and camera changes do not invalidate the input context; a focused label removed by camera projection still releases its own focus.

Duplicate display titles receive a short identifying row using the recorded filename and the shortest distinguishing path suffix. Same-file, same-line objects use acquired source ranges first; remaining collisions use existing ID suffixes. Source-less objects use their known kind, group and ID. Tooltips retain full identifying information, and details retain the original name, source ranges and Evidence. These strings also identify search results in both modes; canonical names, IDs and relationships stay intact. The 2D implementation adds role/identity text within the existing card dimensions and changes emphasis opacity while preserving card positions, ports and curve geometry.

Both stages share Module Dependency's dark green background without a grid. In 2D, visible lines, arrows and particles are painted above node cards; transparent edge hit targets remain below cards so crossing lines do not intercept node selection. In 3D, label projection refreshes the camera world matrix before using it, since OrbitControls changes orientation before the WebGL renderer refreshes that matrix. Existing DOM labels receive CSS-pixel transforms in the same frame; React updates only label membership and content. Late-mounted labels use the latest position, and culled labels immediately leave display, pointer and keyboard interaction. Layer suspension ignores late frames and supports effect cleanup/remount.

Semantic connections use cubic curves, including a gentle arc for single relations. The SVG line, hit target and particles share the same curve definition; 3D lines and particles share samples from that curve. Particles advance at a constant arc-distance speed with 50 world units between particles (100 in reduced mode), independently of connection length. SVG round dashes provide the 2D particles without allocating a DOM node per dot. The shared GPU particle renderer accepts this fixed spacing for Views 6–7; its default bounded layout for Module Dependency remains unchanged. SVG edge focus uses a stroke along the curve, with the browser's rectangular outline suppressed for both pointer and keyboard focus.

For 3D, curve endpoints and arrow tips use the canonical point centers, including self-relations. This avoids the former world-space endpoint shortening diverging from the screen-sized points during zoom. Arrow and particle geometry use the same sampled curve, while a displaced label's leader separately connects to the point. The 2D endpoint and curve branches retain their existing geometry, covered by a pre-change golden snapshot.

`AnalyzerViewSession.explorer` stores visits with 2D scope/center/depth, 2D camera and scroll position, 3D camera, mode, canonical selection and detail-open state. A route state stamp identifies the visit; URL fields describe its destination. Back/Forward restores those recorded states within the current scan/session. Query, global filters, the effective direction setting and particle mode remain common state and are not rewound by visit history. Parent climbs ownership; project and breadcrumb actions create a visit at the corresponding scope. Pan, zoom, scroll and ordinary node/edge selection update the current visit without adding browser history. `semanticExplorerJump` distinguishes explicit related-View destinations from ordinary tab restoration.

`flowCameras` stores affine 2D and orthographic 3D position/target/zoom separately per View. Normal mode changes restore each mode's saved place and camera while retaining common selection, query, filters, direction and particles; evidence follows the retained canonical selection. Explicit cross-mode actions prioritize the requested canonical ID. An existing selection on a first 2D visit opens the selected node's ownership and local diagram, or the selected edge's source context. A first 3D visit focuses the selected node or both selected-edge endpoints. Search and explicit node jumps into 2D use its local initial camera. Stage commands are tied to a mode/visit so a stale Fit or focus does not replay on a normal return, while lazy-loaded 3D still receives a new explicit focus.

3D projection offsets center the target below navigation and above the legend without changing the stored camera position or orbit target. Fit uses the available plot height. OrbitControls keyboard changes are saved explicitly because they do not emit a pointer gesture end. Legacy Orbit camera state is migrated only to 3D. Fit frames the displayed targets/curves; focus is a separate command. 3D initialization failure or context loss returns to functional 2D with semantic state intact. Escape on a normal focused 2D/3D canvas clears selection; the ancestor fullscreen handler handles the first Escape to leave fullscreen while retaining selection. The 3D canvas handler ignores composition/input events and is removed on disposal. Fullscreen preserves selection and restores page focus on exit.

## Verification

Run `pnpm test`, `pnpm typecheck`, `pnpm lint` and `pnpm build`. Real-WASM tests cover language declarations/calls, model fields, import aliases, nearest lexical/class resolution, unknown receiver counterexamples, named callbacks, registration ownership, nested/fluent calls, branch/merge preservation, full Schema ranges and routes. Projection/trace tests cover exact supplied clocks, recorded parent correlation, durations, explicit data lineage, View separation, complete summary provenance, cycle depth and evidence immutability. Search tests cover explicit fields/ranking/normalization and 10,000-result virtual navigation. Page tests cover query/camera independence, separate mode cameras, source/target evidence navigation, hidden selection, trace reset and retry.

To opt into read-only repository validation, set `WEB_ATLAS_VALIDATION_REPOS` to semicolon-separated absolute repository paths before running tests. The reader skips symlinks and excluded directories and does not run target code or write to those repositories. `WEB_ATLAS_VALIDATION_SNAPSHOT=1` additionally writes masked store/analysis snapshots only to this project's ignored `.cache/semantic-validation` directory for browser verification. These snapshots are temporary and are not shipped.

The independent explorer source-fact comparison is a separate opt-in: also set `WEB_ATLAS_EXPLORER_ACCURACY_FACTS` to the matching review-facts JSON file. It consumes that report and the existing masked store/analysis snapshots for the configured reference projects. Ordinary repository validation does not require these review artifacts.

The four-fix source/presentation comparison is separately enabled by `WEB_ATLAS_FOUR_FIXES_REVIEW=1` alongside `WEB_ATLAS_VALIDATION_REPOS`, after creating the masked snapshots. `WEB_ATLAS_FOUR_FIXES_REPORT=baseline` records source/snapshot hashes; `final` compares them with that fixed baseline. Its real-project cases retain the review snapshot's specific source examples; synthetic conservation, display-label, viewport-readiness and interaction regressions also run in the ordinary suite.

The five-item point/edge/label/group comparison uses `WEB_ATLAS_POLISH_REVIEW=1` with `WEB_ATLAS_VALIDATION_REPOS` and the fixed masked snapshots. `WEB_ATLAS_POLISH_REPORT=baseline` records source and snapshot hashes, canonical graphs, ownership, 3D vectors and actual-source 2D paths; `final` compares the same inputs. Ordinary tests independently cover endpoint projection, direction roles, counterpart versus individual-edge hover, duplicate identities, input ownership and bounds preference retention. Actual GPU/camera/physical pointer and focus checks are recorded separately from these mathematical and React tests.

Browser verification must separately cover Worker/WASM loading, all five projections, detail navigation, 2D/3D interactions, fullscreen, responsive layout and the execution-data file chooser. Node parser tests alone do not establish browser compatibility.
